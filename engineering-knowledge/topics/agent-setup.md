# Конфигурация, маршрутизация и проверка нового чата

## Реально доступные возможности

На 2026-10-28 установлен Codex CLI **0.163.0**. Формат `.codex/config.toml`
и `engineering-knowledge/agents/*.toml` сверен с официальными источниками именно этой версии:

- [Конфигурация Codex](https://github.com/openai/codex/blob/rust-v0.163.0/docs/config.md).
- [Официальная схема](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/config.schema.json):
  AgentsToml, AgentRoleToml.config_file, developer_instructions.
- [Загрузка ролей](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/agent/role.rs).
- [Документация подагентов](https://developers.openai.com/codex/subagents) — её веб-
  страница недоступна из этого executor (сетевой 403); содержимое не выдаём за прочитанное.

Роль имеет описание и относительный config_file (от каталога config.toml).
Модель, reasoning и права не переопределены. Лимит CLI — 4 потока/глубина1;
облачный orchestration использует собственные лимиты и не обязан читать этот конфиг.
В доверенном checkout CLI использует проектный конфиг; не меняем пользовательский
trust, глобальную конфигурацию, авторизацию или разрешения. Недоверенный checkout
может игнорировать проектную конфигурацию: это не поломка базы знаний.

Текущий облачный collaboration.spawn_agent доступен и использован для двух
независимых исследований при настройке. Его схема **не принимает имя роли**.
Поэтому конфиги не объявляются автоматически подключёнными к нему: координатор
читает профиль и передаёт developer_instructions как содержимое задачи.
Это обычные инструкции задачи, не повышение их приоритета до системного.
Если инструмента подагентов нет, AGENTS и база работают при одном агенте.
Запуск именованных ролей в отдельной CLI-сессии не проверен end-to-end;
TOML/официальная схема и загрузка CLI-конфигурации проверяются отдельно.

## Выбор и обмен знаниями

1. Главный агент определяет инженерные области, ищет их в каталоге.
2. Читает лишь нужные страницы, сверяет статус/условия и исходную реализацию.
3. Простое изменение делает сам; независимые сложные вопросы передаёт профилям.
4. Даёт каждому точную задачу, контракт результата и непересекающийся набор файлов
   записи. Без назначения записи — исследование read-only.
5. Объединяет выводы, проверяет стыки, вносит компактное обновление базы.
   Профильные агенты не являются постоянно работающими процессами и не имеют
   независимой скрытой памяти: их память — соответствующая страница Git.

Новый профиль появляется при новой реальной области: сначала проверить, можно ли
дополнить существующую страницу. Если нельзя — добавить одну запись каталога,
страницу с реальными знаниями/пробелами, TOML роли и запись agents в конфиге.
Не создавать пустые профили ради предполагаемой работы. После появления
AutoSizeDrilling создан sw_dimensions: материал и его статусы — в dimensions.md.

## Пример нового чата: виды компонентов + наименование + PDF

Пользователь просит разместить виды деталей сборки на листах с их наименованиями
и выпустить общий PDF. Через AGENTS новый чат находит каталог и выбирает:

- sw_drawings: контракт листов/активации, размещение видов, сохранение семейств.
- sw_component_notes: исходная модель/конфигурация, контекст компонента и живые
  ссылки. При наличии SectionAssembly использует N3 и GetUniqueName.
- sw_document_output: готовый экспортный контракт O1, безопасные пути и проверки.

Читаются три страницы, а не все исторические версии. Источники дают реальный
CreateDrawViewFromModelView3 и правила привязок, однако обход сборки, подбор
ориентаций/размещение и нативное нанесение размеров на новые виды требуют
собственных испытаний.
Теперь sw_dimensions использует ограниченные алгоритмы AutoSizeDrilling
для подходящих видов одного компонента; сложные виды и новую геометрию исследует
отдельно. См. dimensions.md: численные тесты не означают native-проверку.
Для проверки API/поставки привлекает sw_vba_com при необходимости.
Проверенный PDF helper повторно использует, не исследуя заново сам SaveAs;
страницы/порядок нового PDF всё равно испытывает. После native-теста обновляет
существующие записи или добавляет новый обоснованный профиль со статусом.

## Проверка передачи в чистый контекст

Без истории чата достаточно: открыть репозиторий → прочитать AGENTS → каталог →
нужную страницу → исходную функцию/свидетельство. Контрольные вопросы:

- «Почему пусто наименование разреза?» → component-notes N2/N3 → V21;
  не повторять V20 с root Name2 и отображаемым именем.
- «Можно ли быстрее сохранить оригинал?» → document-output O2/O3 → V22 не испытана;
  не удалять SOURCE для межлистовых семейств и не обещать reopen-проверку при False.
- «Автоматически расставить размеры?» → dimensions M1–M5 и локальный снимок → есть
  C#-кандидат и тесты для ограниченной геометрии; не выдавать их за native-успех
  или контроль GetDimensionCount4 за постановку размеров.

`python3 engineering-knowledge/tools/check_agent_knowledge.py` проверяет локальные ссылки, пути ролей,
каталог и неизменность рабочей V21 относительно зафиксированного коммита.
Это проверка устройства памяти, не доказательство будущего соблюдения инструкций
моделью. Автообновление выполняется во время задач по AGENTS, без фонового сервиса.

0.163.0; структурная проверка нашла 8 документов/4 маршрута, ошибок нет.

AGENTS → каталог → профили → функции и верно определил: ремонт заметок V21
подтверждён, подход V20 не повторять, сохранение V22 нативно не проверено.
Это испытание навигации в чистом контексте, не сквозной запуск именованных CLI-ролей.
